## What was built

**Chat** (sidebar → WORK → Chat, above Tasks):

- **The chat.** You talk to the Team Lead, an agent with Chat turned on (one at a time).
  - Each message is one Claude Code answer, streamed as it is written.
  - Threads are kept, so a thread continues its Claude session.
  - Every tool call shows as a card that links to what it made.
  - Stop ends an answer.
- **Without a Team Lead,** the page explains and offers *Set up the Team Lead*. That opens the agent form on the Team page, prefilled with name "Team Lead", role Lead and Chat on.
- **33 tools.** The Team Lead uses Gizai's tools: overview, inbox, clients and contacts, projects, tasks (create, change, move, comment), agents (create, change, pause), routing rules, starting and stopping agent runs, docs, attaching files, people, workflow. It refers to things by name ("KADE-12", "Kade portal", "Backend Agent"). When a name matches several items, it gets the candidates back instead of a guess.
- **How it connects:**
  - Claude Code starts the small `gizai-mcp` helper.
  - The helper connects to Gizai on a socket only your user can open, using a key that lives for one answer.
  - Every change goes through the same code as the UI, so screens update live, and the activity log says "Team Lead".
- **What the chat can and can't do.** It runs Claude Code in `--restricted` mode: no shell, no file edits, read access to linked repositories only, none of your plugins or hooks.
- **Cost:**
  - each answer is recorded as a run of the Team Lead, so it counts towards its monthly budget;
  - limits per answer are 15 minutes or 60 tool calls;
  - one real Haiku answer cost $0.027 (about 25k input tokens).

**Team page.** "Members" is now an **org chart**:

- the Team Lead on top;
- Development, Design, Quality and Operations below (from the agents' roles; other roles go under Specialists);
- teal ring and "Working" while an agent works;
- dashed empty places for the usual team that open the agent form with that role.

**Agents.**

- New roles **Design** and **DevOps**, with their own instructions and icons.
- The Lead's instructions are written for the chat.
- The agent form has a **Chat** switch.
- The agent page shows *Open chat* and labels chat answers.

## Added on 7 October (your requests)

- **The model is a dropdown of what your Claude Code offers.**
  - Gizai asks the installed `claude` for its `/model` list through the stream-json `initialize` handshake. No message is sent and nothing is spent.
  - The list is kept for 30 minutes; ↻ asks again.
  - Each entry shows its full id, a description and the price; "Other model id…" takes any id.
  - A saved name Claude Code doesn't know (like "opus 5.5") is flagged in the form.
  - The Team Lead's agent tools refuse such names.
- **Effort per agent:** Default, Low, Medium, High, Extra high or Max. It is limited to the levels the chosen model supports (Haiku takes none) and passed as `--effort` to task runs and chat.
- **The board is the default view** of Tasks, and its button comes first. The Inbox stays a list. The saved view setting has a new key, so an earlier "list" choice doesn't hide the change.
- **The headless UI tests point every test copy at the fake Claude Code,** so the model list never starts your real `claude`.

## Added on 7 October, afternoon (commit 0cf6975)

- **The app you use and the dev build are separate.**
  - The installed Gizai (app launcher) keeps your data in `~/.local/share/gizai` and only changes when `./install.sh` runs. It backs up your data first (`backups/gizai-before-install-….db`) and installs nothing if the backup fails.
  - `scripts/run.sh` runs the dev build on its own data (`.devdata/dev`). It runs alongside your app and no longer updates it. A Gizai on other data says so in the window title and at the bottom of the sidebar.
  - One Gizai per data folder: a second start focuses the open window (D-Bus name per data folder), and a lock file refuses a second copy from another session.
  - `gizai --backup [name]` takes a snapshot any time. Opening data from an older Gizai snapshots it before the upgrade. The 20 newest snapshots are kept.
- **Sidebar:** the organisation rail is gone, and Company (Team, Users, Settings) sits at the bottom.
- **Org chart:** the Working badge is an opaque pill with a teal outline.
- **Runs tab:**
  - A row opens to show why the run ended (in full), the agent's last message, start time and duration, model, tool calls, tokens, cost, branch, worktree, and the command to continue by hand.
  - The run card keeps showing the run's reason while the card is on hold.
  - A run that hit a limit is labelled "Hit a limit".
- **Run limits are settings** (Settings → Runs). The default is 60 minutes and 200 tool calls, up from 45 and 80.
  - The agent is told its limits in its prompt, so it can commit in time.
  - Every tool call counts: the old counter counted stream lines, while its message said "tool turns".
  - The error says which limit stopped the run.
- **Holds:**
  - A stalled card's reason names the last error.
  - Clearing a hold resets the failure count. Before, one more failure put the card straight back on hold.
- **Why a real card stalled:** two runs failed on the old free-text model "opus 5.5", fixed by the dropdown. The third used all 80 tool calls in 9 minutes reading a large repository, and was stopped mid-edit. The full report is kept outside this repository: it has client details.

## Added on 7 October, evening (your answers; commits 85606cb, 80d7f8d, 002741a)

- **Runs last 90 minutes** by default. Settings → Runs changes it.
- **Cards at once:** an agent works on 1 to 10 cards at the same time, each in its own worktree (agent form → Wakes up). Heartbeats and assignments fill it up to that number. "Runs at once" in Settings, the cap for all agents together, now goes up to 20. Set it to at least the sum you want running.
- **Continue:** the card's latest run, if it stopped part-way after doing some work, gets a Continue button.
  - Continue resumes that run's Claude Code session in the same worktree, telling the agent why it stopped and to check `git status` first.
  - It clears a hold on the card. Run still starts fresh.
- **GitHub link per project:** the project form has a "GitHub repository" field, filled in from the folder's GitHub remote.
  - With a link, each run first fetches main from GitHub, through your own remote for it (whatever its name, for example `upstream`), never asking for a password.
  - A new card's branch starts there, without tracking, so a push can't land on main.
  - A card that already has a branch is told how many commits GitHub's main has that it doesn't, and to merge them before it finishes.
  - If the fetch fails (no network, or no ssh key available to Gizai), the card goes on hold with the reason.
  - Runs record the commit they started at.

## Final review

A fresh reviewer (Opus) read the whole branch:

- **Verdict:** ready to merge with fixes. No critical issues. All five review-focus behaviours were found implemented and tested, along with the socket and key handling and the layering.
- **Fixed in one pass,** each with a test that failed first; all suites are green again:
  - **The chat could forget a conversation.** A failed resume wiped the thread's session, and a stopped or failed first answer never saved one. Now any answer that got as far as starting its Claude session keeps it, and a failed resume keeps the old session until a new one starts. A thread with history but no session starts a new one with its recent messages.
  - **The chat could unlock an agent.** Through its tools the Team Lead could give an agent `bypassPermissions` or unlimited Bash and start it, and link any folder as a repository, which widened its own read access. Now it can't set those powers (only you can, in the agent form), linked folders must be git repositories (never `/` or your home folder), and only git repositories are opened to it.
  - **`attach_file` could copy any file.** It now takes only files you named in that chat or files inside a linked repository, as the spec says.
  - **`scripts/ui-test.sh` failed on a fresh checkout,** because it never built the `gizai-mcp` helper. It builds it now.
- **Final rulings:**
  - I dropped one old assertion ("a failed first turn leaves no session"), because it encoded the behaviour the review found harmful.
  - The review's "declined to judge" items stand as they are.
  - The two-turn real check is yours to run (see Decisions): it writes a session file under `~/.claude`.

### Deferred minors

- Failed resumed turns can count their cost twice against the budget. Recording totals on any result now covers most of this.
- Stop in a narrow window can mark a finished answer as cancelled.
- A second Gizai on the same data folder takes over the socket. A single-instance guard would fix this and older double-start problems.
- The resolver prefers an exact key over a *different* project's exact name, and `column()` falls back to a category silently.
- `update_task` applies the fields before checking labels, so a bad label half-succeeds.
- A Gizai crash leaves no "interrupted" note in the chat, and crashed chat runs get outcome "error".
- Tool results cut at 4,000 characters become invalid JSON, so the card loses its count.
- The live text snapshot can drop a few words that arrived during the request.
- Old keys (`api_tokens`) and chat logs are never pruned. The key suggestion can produce a 7-letter key after nine collisions. The helper forwards Gizai's refusal line to Claude Code.
