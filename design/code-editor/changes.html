Decisions

Everything here is drawn with the app's own stylesheets (src/styles/), its components (top bar, tabs, rows, badges, Empty, the error banner) and type styles; the new parts use tokens only. The code is parsed with Lezer's own grammars and coloured with the new tokens, so it shows what CodeMirror will show.

  1. Changes is a tab at the top of the card, full width. Card | Changes sit right under the top bar, so you see at a glance whether a card changed anything and how much (+3,695 −69). A tab next to Comments would put the diff at the bottom of a 920px column; a panel beside the card leaves about 55 characters of code. Full width gives about 110 characters at the usual 1440px window. Properties closes on Changes; ] still brings it back. The address is #/task/GA-118/changes.
  2. The file list is the Memory page's explorer. 260px on side, rows of 28px like the Memory tree, files under their folder (the folder's full path, folders first, then files at the top level), each with a status letter, its counts and a dot when it isn't committed yet. Where the changes come from sits on top, in a sentence. It folds with [ (the twin of ] for Properties).
  3. Every file below each other, in boxes. Each file is a box with a header that sticks while its diff is in sight: path, counts, why it's folded, Open. Boxes make the edge between two files obvious in a long scroll (the largest card here changed 245 files).
  4. One line-number column. As the research found, CodeMirror's unified view has one; an added or unchanged line shows its number now, a removed line its old number, in red. With the + and − marks that reads without a second column, and it leaves room for code.
  5. Folds say what they hide and step by 20. "37 unchanged lines" shows them all; ↓ 20 continues down from the change above, ↑ 20 up from the change below. Short folds (20 lines or fewer) have only the count. A fold that can't open (GitHub's diff) says why.
  6. Big, lock, deleted and binary files say what they are. Lock files, diffs over 3,000 lines and deleted files over 40 lines come folded with a Show button and a word in the header; a file over 1 MB says it's too big and offers your editor; a binary file gives its sizes; a rename without changes is one line.
  7. Colours: four hues for code, green and red only for changes. Violet keywords, blue functions and tags, gold types and attributes, orange strings and numbers; names in text, punctuation in text-2, comments grey. No teal or magenta (an agent at work, needs you), and no green or red in syntax, so a green line always means added. The values come from the decorative c-* colours where they pass 4.5:1, and every text colour passes 4.5:1 on bg and raised in both themes, and on changed lines too.
  8. Nothing relies on colour alone. + and − marks, old numbers on removed lines, A M D R letters with their word in a tooltip and for screen readers, "Not committed" in words in the file header, a wavy underline under code the parser can't read.

1. The card, with its Changes tab

The page as it is now, under two new tabs: Card (Lucide square-kanban) and Changes (file-diff) with the counts, which load with the card (card_changes, the file list only). The Pull request panel gets the same counts and Show changes; each run with commits gets Show changes in the Runs tab (the row becomes two buttons side by side: open the run, show its changes).

2. Changes

GA-118, a Gizai card in Review: 10 files with one of each kind. Try the carets, the folds (the top one in sidebar.ts, the long one in Sidebar.tsx), Show on the folded files, a click in the list, the filter, and the keys after a click in the frame: n p, Alt ↓ Alt ↑, [.

How it behaves

  • Scrolling. The list and the diffs scroll on their own. The current file in the list (selected) follows the scroll; a click in the list scrolls its file to the top. A file mounts its editor only when it comes near the screen; until then its box has its header and the height its rows will take.
  • Keys (while the view has the focus): n and p the next and previous file; Alt ↓ and Alt ↑ the next and previous change (F1 binds goToNextChunk and goToPreviousChunk); [ folds the file list; Esc goes back to Card; ] shows Properties.
  • The filter narrows the list and the diffs to paths that hold its text; with no match: "No file matches “…”. Clear the filter". The heading then reads "3 of 10 files".
  • Open opens the file in the Editor at that change. It shows only while the card's worktree is there and the Editor (F2) is built; Open in on the top bar offers VS Code, Zed or PhpStorm (D2, B2).
  • Long lines scroll sideways inside their file; the numbers stay put (CodeMirror's gutter). A removed block of more than 3,000 characters shows without syntax colours: CodeMirror skips them to stay quick (syntaxHighlightDeletionsMaxLength).
  • Changed words are marked when the old and new line share enough (CodeMirror's own diff on the hunk); a line rewritten from scratch is just removed and added.

3. One run's changes

Show changes on a run opens the same view, limited to what that run committed (run_changes: from the commit it started at to the one it ended at). The list's heading says whose run and when, lists its commits, and All changes goes back. The tab keeps the card's own counts. The address could be #/task/KADE-41/changes/run/<run id>.

4. Empty states and errors

Each says what is going on and, where there is one, offers the one thing to do. A failure goes in the error banner, as everywhere in the app. While the file list loads, the heading says so; a file that is still loading, or failed, says it in its own box, with Try again.

5. Where the changes come from

The list's heading names the source when it isn't the card's own worktree (research §3.2 Q1), so a merged card never looks like work in progress.

9. PHP, Blade, TSX and Rust

Parsed with @lezer/php, @lezer/html, @lezer/javascript (JSX and TypeScript) and @lezer/rust. Blade is HTML with PHP inside {{ }}, {!! !!}, a directive's brackets and @php, the way F0's Blade language will read it: directives as keywords, the delimiters as meta, {{-- --}} as a comment.

10. Rules for design/README.md

F0 adds this under Visual foundations, after "Colour carries meaning, never decoration". The same text is in design/code-editor/README.md.

Code and diffs

Code (the Changes view, the Editor, code in Markdown) has colours of its own: syn-* for syntax and diff-* for changes. They appear only inside code: never on buttons, badges, status, labels or charts.

  • Changes are green and red of their own. An added line has diff-add-soft behind it and a removed line diff-del-soft; the characters that changed get diff-add-strong or diff-del-strong on top. The + and − marks, a changed line's number, the A and D letters and the counts (+964 −112, in mono) are diff-add and diff-del. A fold bar is diff-fold with text-2. They're near success and danger but separate: those mean run and form outcomes, so neither stands in for the other.
  • Syntax uses four hues and the greys. Violet syn-keyword (and syn-meta), blue syn-function (and syn-tag), gold syn-type (and syn-attribute), orange syn-string (and syn-number). Names stay text, operators and punctuation text-2, comments syn-comment. syn-invalid is danger with a wavy underline.
  • No teal or magenta in code: they mean an agent at work and "needs you". No green or red in syntax: they mean added and removed.
  • Contrast: every syntax and diff text colour is at least 4.5:1 on bg and raised in both themes, and on changed lines; on a changed word every one but comments (3.4:1 in dark) and syn-invalid. Check a new value against all four before it goes in.
  • Never colour alone: changed lines keep their + or −, removed lines their old number, status letters their word (tooltip and screen readers), and "Not committed" is written in the file's header.
  • Type: code is t-code in --font-mono, which Settings → Appearance changes as everywhere. No italic or bold for syntax: the bundled fonts have no italic, and colour already does the work. In text, write arrows with Lucide's arrow-right: → isn't in Atkinson Hyperlegible's files (↑ and ↓ are).

11. For F0 and F1

  • F0: design/code-editor/new-tokens.json holds the 21 tokens in design/tokens.json's format (after c-grey); then node scripts/tokens-css.ts. The aliases ({text}, {syn-string}…) work on :root as st-review does. The tag map is in section 8; Blade as in section 9.
  • F1: the first part of design/code-editor/changes.css is the view's CSS, all tokens. Sizes: tabs as .tabs with 16px sides; file list 260px on side; folder rows 26px and file rows 28px (+ --ui-box); file header 40px (+ --ui-box) on raised, sticky; boxes radius-l, 12px apart, the column padded 12px 20px; code t-code (12.5px/20px); the number column as wide as the file's longest number plus 20px, then 18px for the mark; fold bar at least 28px.
  • Thresholds (research §3.2 Q2): 3 lines of context; folds of 4 lines or more; steps of 20; folded from the start: lock files (package-lock.json, composer.lock, Cargo.lock, yarn.lock, pnpm-lock.yaml), built files (dist/, build/, *.min.js, *.map, linguist-generated in .gitattributes), diffs over 3,000 lines, deleted files over 40 lines; too big over 1 MB a side (tooLarge).
  • Rebuild this page with node design/code-editor/gen-changes.mjs (its first lines say how until F0 installs the PHP and Rust grammars).
