# Handoff, 7 October 2026: Gizai builds Gizai from here

This is for the agents that work on Gizai from inside Gizai, and for Jeffrey. It sums up the long research and build session that made v0.1 to v0.3, so you don't need that session's history. The rules are in `CLAUDE.md`. The open work is in `docs/OPEN-ITEMS.md`.

## What Gizai is today

A local desktop app (Tauri 2, React and TypeScript, Rust, SQLite) for one person and their AI agents.

- **Work:** clients with contacts, projects (each linked to a local git repository and optionally to GitHub), and tasks on a board or in a list. Tasks have comments, activity, files, docs and an Inbox ("needs you").
- **Agents** are Claude Code (`claude -p`, headless) with a role, a model, an effort level, instructions, allowed commands, a monthly budget and a number of cards at once. The columns they are on decide when they start (GA-49); the Team Lead also has its chat and board check.
  - Each card runs in its own git worktree on its own branch.
  - Each column (Team → Workflow) holds its agents, is Auto or Manual, and links to its next column; the workflow gates move a card along the links: To do → In progress → Testing (QA agent) → Review (Jeffrey) → Deploy → Done. Labels are tags for people and route nothing (GA-49: routing rules are gone).
  - A run ends with a `GIZAI_RESULT` line, and Gizai moves the card on from it.
- **Runs:**
  - Limits are 90 minutes and 200 tool calls (Settings), and the agent is told them.
  - The Runs tab shows why a run ended and the commits it made (it saves the commit a run started at and the one it ended at). Continue resumes a stopped run's session.
  - Three runs without a result put the card on hold (stalled); clearing the hold gives it fresh tries.
  - With a GitHub link, new cards start from main fetched from GitHub.
- **Chat:** the Team Lead (one agent with Chat on) answers in the Chat page. It works through 33 Gizai tools over MCP (`crates/gizai-mcp`) and can create and change clients, projects, tasks and agents, write docs, attach files, read the Inbox and start runs. It runs `--restricted`: no shell, no file edits.
- **Team page:** an org chart built from the agents' roles.
- **Safety:**
  - One Gizai per data folder.
  - A snapshot before every install and every schema upgrade (`gizai --backup [name]`).
  - Agents run without Jeffrey's hooks and skills.
  - The dev build (`scripts/run.sh`) runs on `.devdata/dev`, separate from the installed app.

## How it's tested

- **`cargo test --workspace`: 212 tests.** They cover the core, agents, MCP, chat turns and runs. Runs use the fake Claude Code `crates/gizai-agents/tests/fake-claude.sh`. Its prompt words FAKE_HANG, FAKE_CRASH and FAKE_NOT_LOGGED_IN change what it does.
- **`npm test`: 92 tests** of UI logic.
- **`scripts/ui-test.sh`: 6 headless probes in `cage`** against a copy of `.devdata/demo`: the board, the task editor, a doc, team, a run and chat.
- **`scripts/test-install.sh`:** the installer, against a scratch home folder.
- **`scripts/single-instance-test.sh`:** one Gizai per data folder.
- **`scripts/shot-cage.sh <route> <out.png> [data]`:** headless screenshots. With `MODE='steps:<css selector>;#/route'` it clicks and navigates in order.

## Decisions already made

These are in `docs/v0.3-notes.md`, with the reasoning:

- One chat agent (the Team Lead), which hands coding to agents as cards.
- Task agents run without hooks and skills (`disableAllHooks`, `--disable-slash-commands`, `--setting-sources user`).
- Run limits are 90 minutes and 200 tool calls; cards at once is 1 to 10 per agent and up to 20 in total.
- The model is picked from Claude Code's own list, with an effort level per agent.
- The board is the default view of Tasks.
- The app is installed per user by `install.sh` (no sudo); updates are deliberate and back up the data first.
- **Worktrees (GA-30):**
  - Before the agent starts in a new worktree, Gizai prepares it with the project's settings (project form → New worktrees): it copies the listed paths from the main checkout (`cp --reflink=auto`; a path the checkout doesn't have is skipped), installs what is missing (`composer install` without `vendor/`, `npm ci` or `npm install` without `node_modules/`; on unless switched off), then runs the setup command.
  - An install or setup command that fails holds the card "blocked" with its output. No run starts, so it isn't a failed run, and the next start prepares again.
  - A new card takes over the worktree of a Done or Cancelled card of the same project, the most recently finished first, so its build stays warm. It gets its own branch, and `git clean -dx` removes everything else of the finished card except the copy list and `vendor/`, `node_modules/` and `target/`. A worktree with uncommitted changes or untracked files, or with an agent in it, is never taken over.
  - On a taken-over worktree the copy step only fills in missing paths, and the install runs again only for a missing folder or for a lock file that changed since the finished card's last commit (`composer.lock`, `package-lock.json`; without one, `composer.json` or `package.json`). The setup command always runs again: the card starts from a newer main, so migrations and builds are due.
  - Settings → Data lists the worktrees of Done and Cancelled cards with their disk use and removes them after you confirm, with the same code as the clean-up after a merged pull request (`worktree::remove_card_worktree`). The branch goes only when main has all its commits.

- **Coding CLIs (GA-3):**
  - Settings → Coding CLIs keeps the built-in Claude Code (its program is still the `claude_bin` setting) and a list of more CLIs in the `clis` setting, so no schema change. Each has a name, a kind (Claude Code, Codex, Gemini or Other), a program and environment lines; a second account is the same kind with its own environment, like `CLAUDE_CONFIG_DIR=~/.claude-2`. An agent's `adapter` is the id of its CLI (`claude_code` for the built-in one), and every run records it.
  - Codex runs as `codex exec --json` with the prompt on stdin. Its modes are sandboxes: `workspace-write` (the default; Gizai also lets it write the repository's git folder, where a worktree's commits go, and use the network), `read-only`, and `danger-full-access` (no sandbox). Effort is `model_reasoning_effort`. Continue uses `codex exec resume <thread>`; the thread id comes from its `thread.started` event.
  - Gemini runs as `gemini --output-format stream-json --skip-trust`, with the prompt on stdin and Gizai's session id (`--session-id`, `--resume`). Its modes are approval modes: `auto_edit` (the default), `yolo`, `plan` and `default`. The agent's `Bash(cmd:*)` commands become `--allowed-tools run_shell_command(cmd)`.
  - An Other CLI gets its arguments from Settings: `{prompt}` is the prompt (without it, the prompt goes in on stdin) and `{model}` the agent's model. An agent without a model loses `-m {model}` with its option, and `--model={model}` alone. Its output is read as plain text, and the end of it is the result, so the `GIZAI_RESULT` line still moves the card. It has no session, so Continue is off.
  - Continue resumes a run on the CLI that ran it, since the session lives in that program and account. An agent moved to another CLI since (another account included) can't continue the run: Run starts the card fresh.
  - Codex, Gemini and Other CLIs report no cost: their runs count $0 against budgets. Tool calls count for Codex and Gemini; the time limit applies to all.
  - Chat stays on Claude Code (it needs Claude Code's MCP and streaming), but the Team Lead can run on any Claude Code CLI, such as a second account. The Team Lead's tools can move agents to Codex or Gemini (`runs_on`), but not to an Other CLI, and can't set `danger-full-access` or `yolo`, like `bypassPermissions`.

- **Updates (GA-1):**
  - Gizai updates from GitHub Releases only, never from `main`. A release is a `vX.Y.Z` tag on `production`, made as `docs/RELEASING.md` says.
  - The release check reads GitHub's latest release with curl: 20 seconds after start when it is due, then every six hours while it is on (Settings → Updates), and on Check now.
  - Update to X.Y.Z, above Company in the sidebar:
    1. fetches only that tag into `<data folder>/update/source` (kept, so later builds are quicker);
    2. builds it with the release's own `install.sh --build-only` at low priority;
    3. backs up the data;
    4. installs with `install.sh --skip-build` into the prefix the running Gizai came from (desktop entry and icons in `<prefix>/share`);
    5. checks `gizai --version`, then offers a restart.
  - A step that fails changes nothing that is installed, and says why.
  - Only a Gizai running as `<prefix>/lib/gizai/gizai` updates itself; dev and test builds never install.

- **Card flow (GA-32):** Backlog → To do → In progress → Testing → Review → Deploy → Done.
  - Columns (GA-49, `columns.rs`): each holds an ordered list of agents (`column_agents`), is Auto or Manual (`workflow_states.auto`) and links to its next column (`next_state_id`). Backlog, Review, Done and Cancelled take no agents and are never Auto; an Auto column must have a next column. New teams get the seven columns linked in order, with To do, In progress and Testing on Auto and Deploy on Manual; a new agent lands on its role's usual columns (builders To do and In progress, QA Testing, DevOps Deploy, the Team Lead none). Migration 0011 turned 0.2.0's routing into this setup.
  - The queue: in an Auto column the agents on it take its cards (`workflow::waiting_for`) whenever a card lands in a column, a run ends, and once a minute, up to their cards at once and the Runs at once limit. Best means priority urgent → low with none last, then cards assigned to the agent, then column and card order. A card assigned to an agent is started only by that agent, also when it isn't on the column. A Manual column starts nothing by itself: Run starts the picked agent, else the card's agent assignee, else the column's first agent. An agent's old wake-up setting changes nothing; there is no worker heartbeat.
  - A card in a To do-type column (category `ready`) moves to that column's next column, as the agent, once its run's process has spawned (from Backlog, when a person presses Run, to In progress). Cards in other columns stay while the agent works; the role's done answer (`ready_for_testing`, `qa_pass`, `deployed`) moves them to the next column, and a run that moves a card into Review assigns it to the person who reviews. `qa_fail` sends it back to the column it came from.
  - Removing a column (Team → Workflow, in the app only) moves its cards to a column you pick, bridges the links to it, takes its agents off and keeps it as deleted, so old activity keeps its name.
  - A card whose last run was stopped (Stop, or Gizai quitting) isn't pulled again: Run or Continue starts it. A card assigned to another agent is left to that agent; a person's assignment (the review's) doesn't stop the queue, so a card dragged back from Review is picked up again.
  - A start nobody watches (the queue) that can't work (Claude Code missing, a wrong model, no repository, a worktree that can't be made or prepared) holds the card "blocked" where it was, without adding to `fail_count`. So does a run that fails because Claude Code isn't logged in: the card goes back to the column it came from. A person's Run shows the error instead of holding the card.
  - After such a start, or after any run that failed, the agent stops taking cards from the queue, so one missing login holds one card. The queue asks before every start, and a queued start asks again just before its process spawns. Only the failure that paused the agent holds its card: a card the queue started just before, which then fails the same way, goes back to waiting where it was, without a hold or a failure. The pause ends when a person starts the agent (Run or Continue), edits it or sets it active (Team page or the Team Lead's tools), or when Gizai starts again. A start that only has to wait (cards at once, Runs at once, a paused agent, its budget) never holds a card.
  - Every card has a Testing switch, on by default. Off: the card skips Testing columns (its next column after a Testing column), so it goes from In progress straight to Review, assigned to the person who reviews, and QA never starts.
  - A DevOps run never sends a card to QA: its `ready_for_testing` moves a card in To do, In progress, Testing or Review to Review, assigned to the person who reviews, and leaves the implementer as it was.
  - Deploy (category `deploy`, added with Team → Workflow → Add column or the Team Lead's `add_column`) is merged, not deployed yet. It is Manual by default: Run starts the card's agent assignee, else the column's first agent (DevOps Agent), and the card stays in Deploy while it runs. The DevOps Agent's `deployed` moves it to Deploy's next column (Done); on a card elsewhere it holds the card, except in Backlog, Done or Cancelled.
  - A merged pull request moves a Review card to Review's next column (with none: the team's Deploy column, or Done when the team has none). On an Auto column its agents pick it up; on a Manual one nothing starts.
  - Migration 0007 rebuilds `workflow_states` and `runs` to widen their CHECKs, keeping every id. Migrations now run with foreign keys off, as SQLite's table rebuild needs.

- **Archive (GA-43):** only a card in Done can be archived (Archive on the board's card, on hover or focus, or on its page), and not while an agent works on it.
  - Archiving sets `tasks.deleted_at` (no migration) and adds a `delete` change, which says who did it (`archived_by`). Nothing else changes: column, comments, runs, files, branch and identifier stay.
  - Archived cards are left out of every list, count, the Inbox and the queue. The Tasks page's bin (`tasks::archived`) lists them, the most recently archived first. A toast's Undo, or Restore on the card's page, puts the card back at the bottom of its Done column.
  - An archived card is read-only: moving, editing, labels, comments, files and runs are refused ("GA-12 is archived: restore it first").
  - Settings → Data still lists its worktree, and a new card can take it over. The Team Lead's `get_task` finds it by identifier (`archived: true`), and `list_tasks` takes `archived: true`.

- **Agent folders (GA-45):**
  - The agent form's Permissions has a Folders list: folders besides the card's worktree that the agent's file tools may read, or read and change (`agent_configs.folders_json`, migration 0009). Only the form changes it: the Team Lead's `create_agent` and `update_agent` refuse a `folders` argument.
  - Refused with a reason (`gizai_core::folders`): `/`, the home folder and the folders above it, Gizai's data folder (this Gizai's and `~/.local/share/gizai`), the folders that hold keys or logins (`~/.ssh`, `~/.gnupg`, `~/.config`, `~/.aws`, `~/.claude*`, `~/.codex`, `~/.gemini`, `~/.local/share/keyrings`, …) with what is inside them and the folders above them, and paths with `( ) [ ] * ? , \`. A link is checked where it leads too. A read and change folder in a project's main checkout gets a warning.
  - Task runs: Claude Code gets `--add-dir` for each folder and `--disallowedTools Edit(//<path>/**) Write(//<path>/**)` for each read folder (`//` starts an absolute path in a rule). Codex reads every folder anyway; its read and change folders become writable roots in workspace-write. Gemini gets `--include-directories` for the read and change folders only, as it can't keep a folder read only. An Other CLI gets none. A folder that is missing, or refused by then, is skipped with a note in the run log (a `gizai_note` line the Run panel shows), and the run starts.
  - The list limits the file tools, not the commands: an allowed `Bash(…)` command can still reach any folder.
  - Chat and the board check: the Team Lead gets its folders with `--add-dir`, after its copies of the code (never the linked folders), and only reads them (Read, Glob, Grep). `src-tauri/src/folders.rs` `lead_may_update` (`gizai_core::folders::may_update`) says whether GA-44's `update_checkout` may update a folder: not when the Team Lead's list sets it, or the closest folder that holds it, to read. `update_checkout` calls it before `start_update`.

- **Agent runs (GA-48):**
  - Each run gets `<worktree>/.gizai-tmp` as `TMPDIR`, `TMP` and `TEMP`, for every CLI (`worktree::prepare_temp`, `TaskRun::temp_dir`). `/.gizai-tmp/` is added once to `info/exclude` in the repository's common git folder; `.gitignore` is never touched. The folder is emptied before a run and when its process group has ended (finished, Stop, a limit), and `git worktree remove` takes it with the worktree.
  - Every task prompt, new and continued, ends with "How this run works" (`prompt::with_rules`): only the rules that hold for the agent's CLI and permission mode. Claude Code's shell rules were checked against Claude Code 2.1.289 in acceptEdits mode with the task-run flags: `$(…)`, backticks, variables, an unquoted heredoc and reaching outside the working folders are refused; pipes, `2>&1`, `&&`, `;`, a quoted heredoc and a redirect into the worktree run. "One plain command per Bash call" and "redirects are refused" turned out false there, so they are not in the prompt.
  - Refused tool calls: Claude Code prints a `system` line (subtype `permission_denied`, with the reason) at each one and lists them in its result line (`permission_denials`). `cli::Parser` shows each as a `Refused` event as it happens, the result line adds the ones not shown yet, and the run saves them (table `run_refusals`, migration 0010: a table of its own, made only when missing, so `runs` keeps its shape). The Run panel shows them as "Refused in this run"; `get_task` and `get_agent` return them. Codex and Gemini report no refusals.

## Things learned the hard way

- **Building:** always run `npm run tauri build -- --no-bundle`. A plain cargo release build can load the dev URL.
- **Graphics:** WebKitGTK on this PC needs `__EGL_VENDOR_LIBRARY_FILENAMES=/usr/share/glvnd/egl_vendor.d/50_mesa.json` (`scripts/run.sh` and the launcher set it).
- **Quitting a test Gizai:** send SIGTERM (`kill <pid>`), never SIGKILL. SIGTERM quits the usual way, which ends WebKit's page process first (`src-tauri/src/quit.rs`). Killed outright, Gizai leaves that process to crash in its own teardown (a WebKitGTK/Mesa bug that leaves a WebKitWebProcess core dump).
- **Window class:** on Linux it is the binary name `gizai`, so the desktop entry is `gizai.desktop` with `StartupWMClass=gizai`.
- **Socket path:** a unix socket path must stay under 108 bytes. The MCP socket falls back to a temp folder for long data paths.
- **Claude Code quirks:**
  - "Not logged in" arrives as `subtype: success` with `is_error`.
  - A wrong model name fails at once with `model_not_found` (cost $0).
- **The run cap counts every tool call.** A big repository can use 80 of them just reading, so commit early.
- **Continue (`--resume`)** is tested with the fake Claude Code only. Its first real use is still to come.
- **Older builds:** never run an older build on newer data. `rusqlite_migration` refuses it, and that is why the installed app and the dev build are separate.
